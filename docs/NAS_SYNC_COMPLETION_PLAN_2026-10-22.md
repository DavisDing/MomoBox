## 2. 原推荐产品边界（D-03 已批准，具体实施以合同为准）

推荐把 D-03 定为：**明确确认的一次首次导入，保留当前库存状态；旧操作历史独立归档，只供查询，不重做库存动作。**

1. 第一期仅允许来源明确的单工作区，将本机现有商品、分类、批次、采购和可表达提醒策略导入同一个已绑定家庭；保持本机商品/批次/采购 UUID，不自动换 ID 或合并同条码商品。
2. 新家庭也须通过现有账号/家庭真实创建流程取得家庭 ID；`create_new_family` 的同步模式字符串不能替代创建家庭，更不能改变已绑定归属。
3. 已有远端家庭允许预检和“补入不存在的对象”；同 UUID 无可靠导入回执的重叠对象、版本差异、软删除和来源不明记录一律进入冲突审阅，不把本地数量累加到远端。
4. 本地已成功同步的对象与已接受/未知回执 outbox 不重新初始化。`serverVersion=0` 不是“远端一定不存在”的证明；必须查询远端并核对来源和回执。
5. 保留旧历史为独立的导入档案；与以后真实库存命令生成的操作记录分别标明来源，统一查询时按来源键去重。无批次关联的历史原样保留为未关联档案，不虚构批次。
6. 不包含图片/OCR/说明书二进制、账号凭据、NAS/HA 绑定搬迁、跨工作区迁移、恢复旧 NAS dump 后继续重放、社区共享和分数单位。

首期导入准入建议收窄到来源已核实、无旧待处理/在途/blocked/rejected/未知回执及未解决冲突的工作区。预检可以报告这些阻塞，但不能发送新基线；先按原幂等/冲突流程结算，不能把旧队列标成 completed、删除或自动归入基线。此限制针对导入前的旧现场；已确认导入计划生成的任务按本计划自己的依赖和回执续跑。确有无法结算的旧现场时另出逐项迁移方案，不用首次导入覆盖它。

若只批准“当前量上 NAS”，可以先交付当前状态导入，但界面与验收必须明确“历史尚未迁移”，不能称为完整同步。推荐同时批准独立历史归档，以避免二次迁移时再改变已初始化数量。

## 3. 原候选合同与兼容方案（历史提案，未采用细节不构成现行合同）

### 3.1 持久导入计划和身份

在 Application 层增加独立的导入编排入口，复用现有 Repository、会话检查、同步协调器和 outbox；不把全库扫描放在登录、Provider 构造或普通 `runOnce` 内偷偷执行。

预检只读生成 manifest，至少包含：格式版本、import ID、来源 localWorkspaceId、目标规范化 endpoint/user/family、记录覆盖范围及数量、字段不支持清单、逐条稳定来源 ID、内容摘要、既有远端版本/checkpoint、依赖、用户确认范围。摘要只用于检测变更，不是用户授权或服务端身份。

确认后在本地事务中保存冻结计划、稳定映射和待发任务；网络调用在事务外。每条任务的 operationID/changeId/idempotency key 生成一次后持久化，不能重启或超时后重新生成。持久状态使用明确模型和版本，不能把大批不可查询状态塞成一个无界 JSON 设置值；如需新表，必须提升 Drift schema 并提供升级/回滚兼容测试。

服务端增加导入计划及逐条 receipt 的持久记录，隔离于会过期的普通请求幂等缓存；唯一性至少覆盖 family + 实体类型 + 实体 UUID 的初始化身份及来源计划。第二台手机导入同一备份时也不能因 device 不同再次增加数量。相同身份/内容重试返回原回执，内容不同则冲突，不用覆盖旧 receipt 重新执行。

### 3.2 分类 UUID 与出站依赖

- 本地分类文本保留现有展示；新增持久分类身份/映射，按已绑定家庭作用域保存 UUID，而非每次上传随机生成，也不靠分类名称散列永久代表身份。
- 首次预检以现有远端活跃分类和本机实际分类文本生成候选。远端有大小写不敏感的家庭内唯一约束；大小写、空白或同名歧义不得静默合并，列出原名称与候选供确认。若无歧义才复用已确认 UUID。
- 新分类 UUID 在计划确认时固定。远端并发同名创建失败时暂停相关商品，重新读候选并审阅；不能换 UUID 无限重试或吞掉唯一约束错误。
- 顺序固定为分类 → 商品 → 批次资料/批次初始化；采购和商品提醒依赖相关商品。沿用 outbox 依赖阻塞及失败证据；分类未接受则不发送引用它的商品。
- 分类重命名不换 UUID，保留每商品入站绑定；拆分/合并分类属于后续单独业务行为。服务端已有颜色/排序不能被本机默认值清除；本期不提供颜色/排序编辑。对当前 App 不能表达的字段，预检明确阻断对应对象，或经批准先补兼容保存模型，不能静默丢弃。

### 3.3 首次批次状态通过专用库存命令导入

保留普通实体 upsert 禁止改数量的规则。推荐新增仅供受控首次导入的 typed 库存命令 `initialize_import_batch`（名称暂定），不是开放通用 set_quantity。

该命令只在服务端验证计划授权、家庭成员/设备有效、来源 ID 与内容摘要匹配、目标批次尚未初始化且没有既有业务操作时执行；同一事务完成依赖资料、初始数量、当前数量、状态、版本、change log 和不可重复执行的导入 receipt。已有批次不因“值看起来一样”获得初始化权限。

至少校验：整数件；`0 <= remaining_quantity <= initial_quantity`；discarded 必须 remaining=0；零余量与耗尽状态一致；日期与有效期规则合法；批次产品归属一致。`expired` 只由日期事实表达，不生成伪造过去日期；已报废批次保持已报废，不为允许命令而先标 active。

该操作必须保留 initial_quantity 和 remaining_quantity 的区别。例如原累计 12、当前 5，导入后仍为 12/5；不会先补 12 再重新消费 7，也不会补 5 后把 initial 伪造为 5。初始化审计记录标为导入基线，不冒充一次真实补货；统计不能把基线当作当天购买/消耗。

全为零的耗尽批次及已报废批次也可有合法基线，不借现有“数量必须正数”的 restock 拼出空操作。旧软删除对象不初始化为活跃对象；保留本地 tombstone，远端重叠 tombstone 进入审阅。本期不自动传播来源不明的历史删除到远端。

### 3.4 历史归档与正常命令记录分开

推荐增加追加式 `imported_stock_history` 模型（名称暂定），通过专门导入入口写入；不开放对 `consumption_records` 的普通 upsert。

档案保留 source movement ID、产品/可空批次来源 ID、原始 type、signed quantity、note、原始 occurredAt、来源 workspace/import ID；另记本次 importer、device、receivedAt。导入者是当前已认证用户，但不能被写成旧操作真实执行人。无法确定原时区/操作人时记 unknown，不用本次当前时间填成历史发生时间。

- 本地 `intake`、`consume`、`restock`、`discard` 等类型先逐项建立映射；不能把任意正数等同真实 restock，也不能丢弃不支持的调整类型。未识别类型整条拒绝并保留原记录。
- 相同来源 movement ID + 相同摘要返回原归档；同 ID 不同内容报告冲突。跨手机同 UUID 的副本不重复统计。
- 新执行的库存命令继续维护原 `consumption_records` 和库存事务；逐条建立本地 operation 与服务端 receipt/record 的对应，避免把已有本地乐观历史及远端同一命令各展示一次。
- 历史写入、历史拉取或历史补页不得触发库存命令，不改变 batch quantity/initial/version；库存基线和历史合计不要求相等，缺少旧历史时明确覆盖不完整，不编造平衡记录。
- 为完整新设备恢复增加有界分页的历史读取/增量合同；与库存快照使用一致的截止 cursor 或独立历史高水位，不能因历史未读完提前显示完整导入成功。档案写入/读取需家庭权限及游标校验，不能把未知实体直接塞给旧客户端的严格快照适配器。

### 3.5 字段覆盖与协议门禁

预检逐项列出本机与 NAS 差异：商品 category/location/unit/lowStockThreshold，批次 batchNo/isOpened/日期来源和累计数量，采购 category/reason/完成状态，提醒确认和历史。每项必须明确“保持并可同步 / 仅保留本机 / 阻断导入 / 需新增字段”；不能以 HTTP accepted 当成字段完整保存。

实现前冻结新的请求/回执 DTO、完整字段矩阵和错误码。建议以明确的新 feature capability 协商启用导入/历史；未支持时只提示升级并保留本机现场，不退化为危险旧命令。当前客户端严格检查 wire schema/protocol 1/1；不能只改成 2 就声称兼容，具体版本与旧客户端支持矩阵由合同包一并确定。

PostgreSQL 以新的 additive migration 增加所需表/约束，不改已应用 `0001`～`0006` 的 SQL/checksum。版本号在实施时以实际仓库最新值分配。回滚程序不得降级到不认识已应用 migration 的镜像；失败保持既有隔离并选择已验证的前向修复。

### 3.6 原日期候选方案（D-04 已批准，实际实现见第 9 节）

推荐生产日/到期日始终为 `YYYY-MM-DD` 的日历日期；事件时间单独为带时区的 instant。导入前显示按日字段，不把已有日期先转 UTC/本地时区后取日期。当前 `_dateOnly` 使用 `toLocal()`，不能宣称跨时区已正确。

先批准“传输保留原日历年月日，不因旅行改变到期日”；家庭判断“今天”的时区及跨时区展示规则仍需明确。若历史 SQLite DateTime 已失去原日历来源，只列出不确定项人工复核，不批量回写推测值。在 D-04 选定前，相关日期合同/数据转换不进入实现。

## 4. 失败、中断与取消

推荐状态为 `draft → awaiting_confirmation → prepared → sending → awaiting_snapshot → completed`；任何阶段可进入 paused/blocked，记录具体原因和逐项回执。状态名称为提案，不替换现有已验收状态。

- 确认时、每次发送前和本地应用事务内复检持久归属、当前会话、计划版本/摘要；旧会话迟到响应不得推进新计划或写业务。
- 同步协调器在生成和入队关键阶段串行；本地业务有新增修改就使未确认预检过期，要求重新预检。已冻结计划后的新离线操作仍用原 outbox；在基线依赖未完成前不得越过它发送，也不能同时把同一旧操作计入基线和新增命令。
- 未知网络回执先以原 key/receipt 查询或重试；不生成新的 restock，不清队列/游标，不将 rejected 自动改 pending。
- 每条服务端任务事务失败整体回滚；跨多条/多页已经接受的任务保留，暂停后从已持久回执继续。客户端不能用“取消”删除已接受远端业务，也不能把已发送计划回滚成从未执行。
- 用户选择 keep_local_only 或切身份立即停止后续发送；已到达旧 NAS 的命令仍可能被接受，返回原身份后核对原回执。取消不解绑工作区、不清本地数据。
- 仅在全部必需任务/历史页完成、无未解决错误、取得新鲜权威快照并按既有 scope 静默及同事务 cursor/完成标记规则应用后显示完成；字段或历史被排除则显示明确的部分完成报告。
- 同 URL 换服务端或恢复旧 dump 不在本期保护内。没有 server instance/restore epoch 时不能安全自动恢复首次导入；该情况转 D-07，维持暂停，不能凭 endpoint 相同继续重放。

## 5. UI 影响与数据兼容

建议复用同步设置页既有卡片、确认弹窗、进度/错误和冲突入口，增加“预检既有数据”“审阅导入计划”“继续/暂停”及覆盖报告；保持导航、布局、主题和既有控件视觉。确认弹窗须列目标家庭、数据数量、数量基线语义、历史覆盖及排除字段。

新的审阅状态/按钮与长列表属于功能影响，待 D-03 批准后先交付具体界面稿或现有组件组合供审阅，不借实现方便重设计。服务器已有资料只能由明确冲突决策修改；不新增自动改绑或“清空重新同步”入口。

现有 JSON 核心备份继续排除凭据/工作区归属/outbox/导入计划和回执；可移植的业务历史按备份格式单独规划版本兼容，不能把完整运行现场混入核心备份。导入档案若增加数据库表，旧版本打开/降级、导出/恢复与去重都需测试。

本节和 `nas/05-initial-import-contract.md` 是本批实现的当前状态，优先于第 1～8 节历史核对与候选细节。D-03、D-04 已获用户明确批准，不再需要实现许可。

实际实现的数量初始化通过专用原子 `confirm` 完成，不新增普通 `set_quantity` 或候选 `initialize_import_batch` 命令。服务端一个事务完成依赖资料、数量、归档、change log 和 receipt；客户端仅在所有历史页和新鲜快照完成后标为完成。计划的原 ID、服务端摘要、永久 `confirm_started` 状态在未知结果后保留，不通过换 ID、清队列或清游标恢复。未发送确认的过期计划可以结束并重新审阅，曾发送确认的计划只能核对原回执。

字段覆盖：首次候选仅包括本机未取得远端版本的活跃商品/批次/采购及旧历史；远端已同步对象明确排除初始化。商品位置、单位、阈值、分类，批次号、开封状态、日历日期、初始量/余量，采购分类/原因均保留。分类同名歧义和业务 UUID 重叠阻塞；精确同 UUID/name 分类可复用，已有颜色/排序保存在辅助 payload，App 不提供其编辑 UI。现有远端提醒策略沿用服务端，不被空数组清除；本地提醒确认、媒体/OCR、凭据与运行现场列入覆盖说明。

日期保留 YYYY-MM-DD，不把 date-only 转 UTC 后取日；家庭判断今天默认 Asia/Shanghai，事件仍为 instant。旧 SQLite 不批量猜测回填；非午夜等可检测歧义阻塞，所有导入批次日期逐条展示供人工核对。旧来源已丢失时，午夜值也不能证明没有整日偏差，不能承诺自动恢复原值。JSON 核心备份保留新日历文本，同时明确排除 NAS 独立归档和导入计划/receipt；这些不是可移植的核心备份现场。

未纳入：普通新库存命令历史的完整跨设备合并/去重、同 URL 替换服务端或旧 dump 恢复后的自动续传、改绑/多工作区、媒体迁移、超限分片和完整灾备。没有新增第三方依赖。长期事实仅在取得同提交运行证据后建议局部更新 AI_CONTEXT。
