### 1.2 需要防住的故障

1. 镜像不包含数据库已经应用的 migration，或同序号 SQL checksum 不一致，停机后才发现无法启动。
2. 只有 dump，没有解密 HA Token 所需旧密钥、可运行镜像或可验证配置。
3. 覆盖原库失败，或验证前自动开放服务，使候选库的错误不可逆地影响用户。
4. 恢复旧 dump 后 App cursor 高于新库、相同 cursor 指向不同历史，甚至表面 cursor 更大但历史已经分叉。
5. dump 丢失近期幂等回执，App 自动重发已实际发生的 consume/restock/discard，造成二次扣减或补充。
6. 旧 dump 复活被撤销的会话、邀请、设备、成员权限或 HA 权限。
7. 切换后又回退旧库，丢失新写入；两套后端同时可写，形成分叉。

## 2. 恢复包、加密与 manifest

### 2.1 推荐恢复单元（NEEDS_CONFIRMATION）

每次备份生成唯一 `backup_id`，把下列内容组成可验证的恢复包；任何缺项都要明确标记，不得显示“完整备份”：

- PostgreSQL custom-format dump，包含 migration 记录、业务、身份、权限、change log、幂等和审计数据；逻辑备份不等于完整 PostgreSQL 集群/角色备份。
- 已脱敏部署描述：Compose 配置身份、后端/PG 镜像 digest、平台架构、应用版本、迁移清单、配置键名与非敏感值。数据库用户/权限重建方案独立列明。
- **加密 secrets bundle**：对应版本的 `JWT_SECRET`、`REFRESH_TOKEN_PEPPER`、`HA_TOKEN_ENCRYPTION_KEY`、数据库连接凭据；未来有密钥版本时保留解密该 dump 所需的历史密钥集合。配置文件中的凭据同样必须加密。
- manifest 与验证摘要；如未来启用 NAS 媒体卷，另含同一备份窗口的媒体清单、对象/文件校验和和归档。
- 外部灾备身份注册信息的引用与备份时 epoch，仅作为来源记录，**不得把它当作恢复后的有效 epoch**。

手机上的图片、说明书、OCR、离线意图和其他本地配置不随 NAS dump 自动恢复。HA 的配置、设备和服务生命周期由 HA 自身备份负责；MomoBox 只恢复其连接/权限/审计数据，并在上线前验证配套密钥。

### 2.2 加密与密钥保管（NEEDS_CONFIRMATION）

建议采用受维护工具提供的认证加密/封装机制，不自制密码算法；具体工具、格式、算法参数和版本待选型确认。本任务不新增依赖。

- dump、secrets bundle 和包含家庭/用户细节的私有 manifest 均加密。权限 600、`.gitignore` 和磁盘放在 NAS 上都不能替代备份加密。
- 使用独立的备份加密密钥/接收者身份；不要拿 HA Token 加密密钥、JWT secret 或数据库密码充当备份密钥。
- 解密私钥/恢复口令与备份密文分开保管；至少有一份 NAS 故障后仍可访问的受控离线托管副本，并演练托管恢复。
- 先完成加密、完整性校验和异地副本验证，再将备份标记成功；明文中间产物只在受控临时空间短暂保留。失败清理、快照残留和 SSD 无法保证安全擦除的风险应纳入工具选型。
- 解密只在隔离恢复环境内进行，限制访问与留存时间；不把密钥/Token 放入命令行、工单、日志、截图或本文件。
- 轮换时维护 `key_id` 与适用 backup 范围；先验证新包可解密，再轮换在线值。未过保留期的 dump 若仍依赖旧 HA 密钥，不能先销毁旧密钥。
- HA 加密密钥必须与密文精确配套；恢复时随意生成新值不能解密旧 Token。若旧密钥确实丢失，应显式进入 HA 未配置状态并重新授权，不能伪报恢复成功。
- JWT/refresh pepper 的恢复与上线轮换分开处理，按第 5 节失效会话；配套恢复不表示旧会话必须继续可用。

### 2.3 manifest 最小字段（提案，不是现有格式）

| 字段组 | 内容 |
| --- | --- |
| 包身份 | `manifest_version`、`backup_id`、创建时间 UTC、dump 一致性窗口/备份起止、在线备份或冻结写入、操作者/流程记录引用 |
| 来源 | source instance ID（未来能力）、来源 epoch、环境标识、家庭范围；敏感标识只放加密私有部分 |
| 数据 | dump 文件名、字节数、明文/密文 SHA-256（明文摘要置于私有部分）、dump 格式、PG server 与 dump 工具版本、编码/扩展清单 |
| 运行环境 | backend image digest、PG image digest、架构、源码 commit（可得时）、`APP_VERSION`、配置描述校验和 |
| 兼容性 | 完整 migration `version/name/checksum` 集合、wire schema、sync protocol、已验证 App 版本/支持范围；不能只写“最高 migration=6” |
| 覆盖 | included/excluded 数据及媒体说明、可验证的每家庭关键数量/业务摘要、change-log 高水位和幂等覆盖边界（可得时） |
| 密钥引用 | secrets bundle 校验和、加密格式版本、recipient/key ID、HA key ID/指纹；**不含原始密钥、密码或 Token** |
| 验证 | dump-list 检查、完整隔离恢复、migration/业务验证分别记录时间、镜像和结果；尚未运行填 `NOT_EXECUTED` |
| 保留 | 保留到期、异地副本状态、外部不可回退注册记录引用；缺失或无法采集的字段标 unknown，不猜测 |

公开外层 manifest 仅保留定位、加密参数和密文摘要等最小信息。SHA-256 只能辅助识别损坏，不能单独证明来源可信；manifest 与文件映射必须由认证加密或签名保护，核对可信 signer/recipient 与 `backup_id`，防止替换或错配。

## 3. 升级前镜像/schema 兼容预检

### 3.1 在停止生产后端前完成

| 门禁 | 检查与通过条件 | 不通过时 |
| --- | --- | --- |
| 镜像身份 | 保存当前已运行 image ID/digest；拉取候选并核对目标架构、可信发布来源、固定 digest；确认旧镜像可离线取回 | 保持生产服务，禁止使用漂移 `latest` 或猜测版本 |
| 数据库身份 | 只读读取当前完整 migration 集合、实际 PG/扩展版本，记录配置指向及备份 ID | 目标不明确则停止，不对生产库尝试 migration |
| migration 兼容 | 当前已应用记录在候选镜像中有相同名称/checksum；列出待应用项、锁/耗时/磁盘成本 | 未知已应用版本、checksum 不一致、未验证降级均阻断；不篡改记录 |
| App/wire 兼容 | 读取当前 `/api/v1/version` 与 `/api/v1/capabilities`；候选在隔离库启动后验证实际版本与支持矩阵 | 环境变量声明或接口数字不是完整兼容证明；不兼容 App 暂停 NAS 写入 |
| 恢复材料 | 本轮恢复包与密钥可获取、可信、可解密；旧镜像和安全回退目标明确 | 不能仅凭 dump 非空/`pg_restore --list` 放行 |
| 隔离演练 | 当前数据副本恢复到独立空库，运行候选 migration，再启动候选验证；必要时使用另一副本验证旧镜像回退组合 | 禁止在生产库上做“试试看”；无结果标 `NOT_EXECUTED` |
| 容量与窗口 | 空间覆盖原库、候选、恢复/升级临时空间、备份和验证副本；测量时间与锁等待 | 无法满足窗口则延期，不删生产数据腾空间 |

**三个版本维度分开记录**：PostgreSQL migration 集合、本地 Drift schema、NAS wire schema/protocol。工作区存在 `0005`/`0006` 不代表 wire `schema_version=5/6`，也不代表某发布镜像已携带它们。

`0005` 的全局 cursor 排序锁/sequence 缓存、`0006` 的库存 initial_quantity 修补须在真实 PostgreSQL 与目标 NAS 上验证。按项目现有约束暂停相关写入、排空旧事务/连接与 sequence 缓存；不能推断新迁移会自动找回历史漏读，或适合直接反向撤销。

### 3.2 必须区分的兼容组合

- 旧镜像 + 原库：保存已运行基线，仍须评估现有故障，不能把“以前启动过”当作完整验收。
- 新镜像 + 原库副本：验证完整升级路径和业务，不只检查 migration 命令退出码。
- 新镜像 + 旧 dump：先按兼容 PG/工具恢复，再由项目 runner 补齐 migration；升级后重新验证。
- 旧镜像 + 已升级库：**默认禁止**；必须有发布级证据证明可兼容，否则只能恢复匹配旧 schema 的独立库。
- 换 NAS/架构/PG 版本：单独演练；本方案优先使用已核对的 PG 16 兼容组合，PG major 升级不是灾备时默认动作。

建议先预演，再在正式窗口冻结服务端写入并取得最终恢复点，复核预演后没有 schema/config 漂移。在线预备 dump 不能承诺覆盖冻结前最后一笔写入。现有 `update.sh` 不自动实现这套门禁，本文也不修改它。

## 4. 独立空库恢复、验证、切换和回滚

### 4.1 推荐环境隔离（NEEDS_CONFIRMATION）

优先使用独立 Compose project、独立 PostgreSQL 卷与空数据库、独立 backend 配置/端口；外部入口仍关闭。不得复用生产 `postgres_data` 卷或生产 `DATABASE_URL`。

既有 `restore.sh` 固定使用生产部署配置，并有原库清理/重启语义，**不得直接将它视作本方案的候选库恢复工具**。后续应新增显式候选目标流程与安全检查，经确认再编码。

推荐状态流：`PRECHECK → RESTORED_ISOLATED → VALIDATED → FROZEN → SWITCHED_CLOSED → VERIFIED → OPEN`。每一步记录目标、backup/image ID、结果、操作者与下一步许可；失败停在关闭状态。这是未来流程设计，非现有自动状态机。

### 4.2 恢复与验证步骤

1. **盘点与保存现场**：记录故障、时间、源/目标身份、当前镜像/schema、所有写入者、最近可信包与可用密钥。原卷可读时先保留独立备份/证据；疑似损坏或入侵时不覆盖唯一现场。
2. **验证包与建立空库**：验证可信签名/认证加密、文件摘要、配套密钥和 manifest；明确确认目标非生产且为空；用兼容版本工具查看 archive。备份 SQL 本身不可信时先隔离审查，不能恢复到生产特权环境。
3. **隔离恢复**：只运行 PostgreSQL，不提前启动可能自动 migration 的 backend。使用错误即终止的事务性 restore；根据部署用户/权限设计恢复 ownership/ACL。失败丢弃或隔离候选并重建空目标，不对原库追加补丁试凑成功。
4. **按目标镜像迁移**：确认恢复后的 migration 与 manifest 对应，经 runner 补齐已审查项；整个链路中间失败即保持不可服务。保留失败日志与升级前候选证据，不通过改旧 checksum 继续。
5. **启动隔离 backend**：关闭普通注册/邀请、定时写入、HA 出站控制与任何外部副作用。现有能力不足以全部禁用时，使用隔离网络/防火墙和受控配置，不能假设测试不会控制真实设备。
6. **完整验证**：检查下表，生成可追溯报告；变更性测试使用另一个可丢弃副本/测试家庭。正式切换候选不混入测试库存、邀请、HA 指令或审计噪声。

| 维度 | 候选验收要求 |
| --- | --- |
| 结构/完整性 | 全部 migration 身份匹配；表、外键、约束、索引、trigger、identity sequence 状态符合目标；恢复无错误，不能只核对文件目录 |
| 业务 | 每家庭关键行数/摘要与备份一致性窗口匹配；UUID 与父子家庭归属正确；quantity/initial_quantity、有效批次、软删除、提醒继承/关闭语义满足已确认规则 |
| 追加记录 | 库存历史、change_log、conflict、幂等/审计记录保留；历史读取/恢复不能再次扣库存；不承诺当前未支持的 App 历史完整恢复 |
| 认证/权限 | 登录与成员/设备隔离正常；核查备份之后发生的撤权/删除；确保旧会话和邀请按安全策略失效，而非自动复活 |
| HA | 使用配套密钥验证解密成功但不输出 Token；验证配置/权限，默认不发送真实控制动作；失败可显式禁用 HA，不伪装成功 |
| 同步 | bootstrap 一致快照与 checkpoint、pull 顺序/分页、原幂等重试、版本/冲突保护、全家庭隔离；验证第 6 节 epoch 故障场景 |
| 可运行性 | health、实际版本、冷启动、连接池/资源、日志脱敏；手机只读验证与受控写入回执分别验收 |

### 4.3 冻结、切换与开放

- **计划内升级**：预演通过后冻结旧后端所有写入，等待在途事务完成并排空连接，取最终 dump/配套包；正式候选须来自这一最终点并重新验证。不能把预演旧副本直接当作无损切换候选。
- **灾难恢复**：不能取得最终点时选最近已验证恢复点，明确公告实际数据损失窗口；保留手机数据供意图审阅，不承诺其可自动补全全部服务端历史。
- 防止 split-brain：停用/隔离旧写入者与直连管理脚本；共享部署锁仅保护该目录的脚本，不是跨主机/跨后端 fencing。
- 关闭公开入口，完成新的历史身份/epoch 登记、候选库绑定与安全会话处理；再使唯一 backend 指向候选库。入口、连接目标、epoch 若无法原子切换，必须在关闭状态分步完成，校验一致后开放。
- 更换路由/DNS 并不保证所有旧连接失效；终止旧连接和缓存指向，确认旧实例无写权限，再对新入口验证数据库目标、epoch、登录、家庭和同步保护。
- 先开放受控验证，再开放用户。恢复期间旧 App 未具备 epoch 协议时，不能开放其自动同步，见第 6.4 节。
- 原库/原卷与原镜像留存为只读证据至确认的保留期，记录最终切换点和实际恢复损失；不要立即删除。

### 4.4 回滚边界

| 时点 | 建议动作 | 数据/身份要求 |
| --- | --- | --- |
| 候选未切换且无生产变更 | 放弃候选，继续旧环境或保持故障隔离 | 已分配的候选 epoch 不复用；原服务历史未变时不必声称发生恢复 |
| 切换后尚未开放写入 | 关闭入口，验证旧库/旧镜像，受控切回 | 若候选历史曾对客户端可见，回切必须再次分配 epoch，不能恢复旧登记值 |
| 新库已接受写入 | 先冻结并保存新库；优先向前修复 | 不能直接切回旧库丢弃新写入；须确认差异合并或明确批准数据损失，重做验证与 epoch |
| migration 部分完成/与旧镜像不兼容 | 不启动旧镜像连接该库；恢复到独立匹配库或审查补偿 migration | 不删除 migration 记录/日志，不直接倒改库存下界，不修改已应用 checksum |

回滚是一次新的受控切换，不等于“把 `.env` 镜像标签改回去”。涉及新数据取舍、补偿迁移或跨历史合并均为 `NEEDS_CONFIRMATION`。

## 5. 恢复后的身份与权限安全

建议灾备上线时主动失效访问/刷新会话，要求重新认证（`NEEDS_CONFIRMATION`）。旧 dump 可能包含备份后已撤销的 refresh token、设备或成员权限；只恢复原 JWT/pepper 而不处理这些记录会复活旧访问能力。

- 可先在隔离环境用配套值验证，再执行已批准的 JWT/refresh pepper 轮换和会话撤销流程；旧 refresh hash 不能迁移成新原始 Token。
- 核查备份后撤销的家庭成员/设备、邀请与 HA 权限；安全审计来源若也丢失，不猜测仍有效，上线前由管理员保守复核。
- HA 解密密钥与认证签名密钥不同：会话失效不能通过随意替换 HA 密钥实现；外部 HA Token 若泄露，应在 HA 侧撤销并重新授权。
- 新库/新环境未完成家庭恢复时，保持普通注册关闭；不让 `first_setup` 因空库暴露而被他人抢占。
- 用户数据与离线意图保留，重新登录不等于清本地库；身份/家庭与数据归属必须显式核对。

## 6. restore epoch：历史不随旧 dump 回退

### 6.1 语义与存储提案（NEEDS_CONFIRMATION，当前未实现）

定义 `server_instance_id` 为逻辑 NAS 的身份，`restore_epoch` 为该实例的历史代次；正常重启、正常备份不变。恢复、克隆成为新服务、或对客户端可见的历史回切必须改变历史身份。cursor 与幂等证据只在相同身份/代次内解释。

推荐使用**独立于业务 PostgreSQL dump/数据卷的耐久灾备登记介质**，保存实例、已分配 epoch 高水位、激活代次、候选目标绑定和审计；可在 NAS 独立受控目录保存，并有 NAS 外部可信副本。若登记介质可能随 NAS 整机快照回退，单独目录本身仍不够，须从外部副本恢复并比对高水位。

- epoch 推荐严格递增分配；数据库只存用于核对的投影，备份内旧 epoch 只是来源证据，不是上线授权。
- 每次恢复先耐久分配新 epoch，再绑定已验证候选；分配后崩溃的值也作废，不能回收复用。
- 激活记录与候选数据库目标共同校验，旧后端失去写授权；单纯把字段加进 capabilities 不能防 split-brain 或在途旧请求。
- 冷启动发现登记缺失、低于外部高水位或与库投影不一致，应关闭 NAS 变更与 HA 控制入口，不自动接受 dump 中值或随机新建身份后开放。
- 严格单调高水位无法可信恢复时，**不得宣称继续原实例代次**。经管理员确认分配全新 instance ID，让全部设备走保护性重初始化，旧代次证据仍保留。
- manifest 可备份登记引用，但普通恢复流程不得覆写外部激活记录。epoch 不用系统时间代替，不靠单独比较 cursor 大小识别恢复。

外部登记的原子写入/持久化、权限、托管、跨主机 fencing 与丢失恢复机制需要另行设计和确认；本文件未新增字段或存储。

### 6.2 拟议协议约束

后续在 capabilities、bootstrap、push/pull、确认和冲突回执中携带并校验 `(server_instance_id, restore_epoch)`；具体字段、错误码与 wire 版本升级须审批，不把本提案当作现有 API。

- push、confirm、resolve 等 mutation 在业务事务开始/提交前均校验预期代次；错误/缺失时阻断，不能仅靠 App 请求前一次 capabilities 检查。
- 响应与本地事务也校验代次/会话，丢弃旧实例/旧代次迟到回执；跨代次不推进 pull cursor、pushAckCursor、不消费旧 checkpoint。
- cursor 即使未变或比恢复前更大，也不能跨 epoch 复用；checkpoint、applied-change 去重和幂等证据都绑定历史代次。
- 不向旧客户端默默降级为“无 epoch”模式；恢复后需显式拦截不支持的版本。正常版本兼容与恢复历史兼容是两个门禁。

### 6.3 验证要求

至少覆盖：旧 dump 恢复到同 URL；恢复库 cursor 小于/等于/大于客户端；dump 带旧 epoch；外部登记缺失/回退；分配后崩溃；目标切换中崩溃；多台旧后端同时启动；恢复后再次回滚；设备换机/长时间离线；旧 App；push 在途响应迟到。每个场景都要求无错误历史写入、无重复库存动作、无未授权 HA 控制，并保持可审计。

### 6.4 当前版本的临时运维边界

**现有程序没有本文的 epoch 契约，不能安全地自动完成恢复后全设备收敛。** 在实施前，旧 dump 恢复后应保持 NAS 同步/HA 写入口关闭或限于明确隔离的验证环境，先备份各 App 现场并制定逐设备处理计划。不以修改 cursor、清 outbox、重登录或 endpoint 绑定代替历史识别。

若无法隔离旧设备的自动写入，候选即使 health 正常也不能按本文标准开放。任何临时人工重绑定/数据迁移方案都需单独确认；不能声称本文已经让现有恢复脚本生产可用。

## 7. App 保护性重初始化与离线意图审阅

### 7.1 检测与保留（NEEDS_CONFIRMATION，当前未实现）

发现历史身份改变，先停该 scope 自动/手动 NAS mutation、旧 cursor pull、bootstrap 自动应用、HA 重试以及在途响应落库。给出“NAS 已恢复，需核对本地操作”的可行动状态；单机/离线基础操作继续可用，并留在受保护的本地记录/队列中。

重初始化不是清库。保存商品/批次/采购/提醒、媒体及所有 pending、in-flight、blocked、rejected、conflict、已接受但可能不在 dump 内的操作与回执。保持原操作 ID/key、scope、版本、时间和状态作为只读审计，不能把旧已接受操作全部改成 pending。

核心 JSON 不包含完整意图，因此后续需要受控的本地恢复检查点/审阅证据能力。该内部保存格式、敏感信息保护、空间不足与崩溃恢复均待确认；本次不修改本地 schema 或导出格式。

### 7.2 推荐处理流程

1. 重新验证 endpoint、实例、账号、家庭/设备归属与兼容版本；不把同 URL 当作同历史。
2. 取得新 epoch 的一致 bootstrap **作为只读审阅基线**，不立刻覆盖当前本地业务。建议独立暂存/预览，不修改活跃库；暂存实现涉及存储设计，须另批。
3. 按依赖顺序列出本地与恢复基线的差异及意图：实体创建/编辑、消耗/补充/报废、采购、提醒、分类和冲突；保持稳定 UUID，未支持映射/历史不得跳过后推进游标。
4. 按下表核实并由用户/管理员选择，记录决策。真实世界的购买/消耗无法只凭回退后的数据库判断；用现存回执、历史、盘点与相关设备资料辅助，不猜测已发生与否。
5. 处理期间继续产生的新离线操作留在本地受保护队列，不能混入旧快照。审阅确认时重新核对精确本地 revision、新 epoch、当前 checkpoint/远端变化；变化则刷新审阅，不覆盖新意图。
6. 只有新代次下 scope 不存在未解决阻塞、依赖完整且确认仍有效时，才按现有 scope 静默原则原子应用权威快照与新同步状态；没有解决的意图保留并暂停远端收敛。最后重算本地提醒，避免旧指纹错误标已处理或重复通知。

| 意图类别 | 建议处理 |
| --- | --- |
| 未发送 pending | 确认目标仍存在、版本/数量/依赖有效后形成新代次计划；不直接自动上传全部旧队列 |
| in-flight/超时未知结果 | 先找新库是否保留原回执；缺少回执不等于未执行，尤其库存动作必须审阅 |
| 本地 accepted、新库回执丢失 | 作为“恢复窗口可能丢失”事项单独核实，不能据本地成功或新库缺失就自动重放 |
| 新库保留且匹配的原回执 | 保留结算证据，避免再次执行；明确代次来源与操作一致性，不能只比较 key 字符串 |
| blocked/rejected/conflict | 保留失败/冲突及结算证据，重新核对目标版本；不能用旧 resolved 回执结算新历史 |
| HA 控制/联动 | 不重放旧开关、scene/script 或物理动作；以当前设备状态为准，必要时用户重新发起新动作 |

### 7.3 幂等与用户选择边界

- **同一 epoch 的普通断网重试**仍使用原 operation/change ID 和幂等 key；不因超时创建第二个库存命令。
- **跨 epoch 的恢复审阅**不得机械重用丢失的旧回执，也不得简单生成新 key 后重发。只有明确核实并批准的待执行动作，才生成绑定新代次、引用旧意图与决策的新计划；原证据保留。
- 用户可继续保持 `keep_local_only`，不上传、不被旧回执重新开启同步；“撤销待同步”是显式保留/取消意图决策，不等于删除历史或回滚真实物理消耗。
- 用户选择采用恢复基线或重建家庭时，需先保存完整本地现场，并说明哪些数据/意图不能自动合并。不能静默以旧备份覆盖本地事实，也不能未经确认把整库当首次导入上传。
- 首次基线导入、分类出站 UUID/旧分类映射、完整历史恢复仍有既有缺口；本方案不宣称这些能力已补齐。缺口影响审阅时暂停该类写入并提示。
- 尽量复用现有同步状态与冲突入口；若恢复审阅需要新增 UI，须说明对受保护 UI 的影响并单独获批，本次无 UI 修改。

## 8. RPO/RTO、保留与演练建议

全部为 **NEEDS_CONFIRMATION**，不是服务承诺或已测性能。建议先以家庭自托管、逻辑备份和人工审阅为基线，按目标 NAS 的实际容量/带宽/密钥取回时间调整。

| 项目 | 建议起点 | 口径与限制 |
| --- | --- | --- |
| NAS 数据 RPO | 不超过 24 小时；重要家庭可选 6 小时 | 每 24/6 小时一次成功且可验证的加密恢复包及异地副本；失败/延迟要告警，调度频率本身不证明达标 |
| 计划内升级 RPO | 目标 0 已接受服务端写入丢失 | 仅在冻结写入、最终包、恢复/迁移/切换均验证成功时成立；不含尚未上传手机的数据 |
| NAS 核心 RTO | 目标 4 小时 | 从故障确认/服务不可用的约定起点至核心 NAS 经验证可服务；登记故障发现时刻避免用晚确认缩短指标；不自动包含全设备收敛/HA |
| App 恢复收敛 | 目标恢复服务后 24 小时内完成在线设备审阅 | 长期离线设备上线时仍单独审阅；数据量、用户确认与未支持能力可能超时，不能为赶时限跳过保护 |
| 保留 | 7 个每日点、4 个每周点、6 个每月点；升级前最终包额外保留至少 30 天 | 按实际风险/容量确认；6 小时方案另定细粒度点；只有新包验证成功后才清过期包，不删唯一可信点 |
| 副本 | 至少一份本机受控副本、一份 NAS 外部加密副本；建议增加离线/不可变副本 | 同 NAS 另一目录/同卷快照不覆盖整机丢失、勒索或管理员误删；托管密钥分离 |
| 演练 | 每季度一次完整隔离恢复；重大 migration/密钥/PG/镜像策略变化前另做演练 | 至少一次模拟 NAS 与本机密钥均丢失、仅靠异地包/托管恢复；演练禁止真实 HA 副作用 |

RPO 以最近可信恢复点与故障前最后已接受写入之间的实际损失窗口衡量；RTO 记录取回、解密、空库恢复、migration、验证、切换各耗时与人工等待。dump 时间戳、health 或备份脚本自测都不能代替这些指标。若业务要求显著低于 6 小时 RPO，另评估 WAL/PITR 与相应密钥/epoch 管理，不在本任务顺带引入。
